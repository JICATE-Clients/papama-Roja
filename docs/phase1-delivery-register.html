How to read this document

Built means the behaviour exists and is covered by automated checks that assert the work order's own acceptance criteria — 2,840 of them run on every change.

Built is not the same as accepted. Those checks prove rules; they cannot prove a screen works in a Food Partner’s hands. So a separate pass was run by hand through the real signed-in application — as an administrator, a volunteer and a Food Partner — and section one records exactly what happened, including what failed.

The client demonstration of the financial controls is the part still to be scheduled: it needs two administrator logins, because its whole point is that one person cannot both prepare and approve.

Section one

The acceptance pass

Run on 26 September against the live system, step by step in the real application rather than in a test harness.

What it found — and why that is the good news

One real defect surfaced, in offline emergency capture. Two devices recording the same token are supposed to flag both and accept neither. In the live system both were instead refused outright by the database, so the duplicate was never flagged at all — the exact outcome the requirement forbids.

The cause was an internal link written to the wrong kind of record. It was corrected and re-tested the same day, and two new automated checks now hold it in place.

No automated test could have caught this. Those tests run against a stand-in for the database, and a stand-in has none of the real one’s rules. It took a person doing the thing for real — which is what this pass is for, and the reason the remaining five checks are worth scheduling.

Section two

The register

Grouped by the five delivery lanes, in the order they were built — each lane depended on the one before it.

Lane 0 — Configuration integrity

4 built · 1 held
RefWhat it doesStatus
Q-1 ₹10 ceiling holds. The voluntary contribution can never be configured above ₹10; an attempt is refused and recorded against the person who tried. Built
Q-2 One limit, not two. The Food Partner's counter screen reads its contribution ceiling from the same setting the server enforces, so screen and server cannot drift apart. Built
Q-3 Every setting change carries a reason. Recorded in the audit trail; an emergency override extended without a reason is refused. Built
Q-4 Missing settings are named, not hidden. The admin dashboard warns which mandatory value is still unset, and the warning disappears only when all are set. Built
Q-5 City lock at registration — the client's decision. The original scope predates the PAN-India token model, which treats city lock as a pilot-phase control to be superseded. The Work Order asks for a choice: a soft warn-and-confirm at registration, or drop it and rely on onboarding control plus the new address capture. Our recommendation is the soft warning. Building either without that answer would be inventing it. Held

Lane 1 — Token and location model

4 built
RefWhat it doesStatus
A-1 Real places, not free text. All 36 states and union territories and Tamil Nadu's 38 districts are held as master data, addresses are structured, and every redemption keeps its own city / district / state snapshot — so correcting a Food Partner's address later cannot rewrite history. Built
A-2 Where a token works, and for how long. Scope runs from PAN-India down to a single PIN code and is checked against the Food Partner's location, never the beneficiary's. Validity is 60 days — counted from issue for donor-controlled tokens, and from distribution for tokens pApAmA hands out, so a token waiting in the pool does not burn its own life. An expired token is permanently dead; the only way back is a controlled reissue, which an administrator approves with a written reason and which mints a new token linked to the original. Revalidation has been retired, as confirmed on 18 August. Built
A-3 Special Care kept separate. A configurable category master, a fixed ₹100 token value, and a Common Special Care Pool with its own eight-line statement. A ₹100 token spent on a ₹75 meal credits ₹25 to that pool and nothing to revenue. Built
A-4 Donor-controlled or pApAmA-distributed, fixed at creation. The mode cannot be changed afterwards, and the donor sees it on their token list along with “Expired — Not Redeemed” wording where it applies. Built

Lane 2 — Financial controls

5 built
RefWhat it doesStatus
F-1 The ₹10 contribution, tracked to the rupee. Every redemption carries a status — collected, waived or outstanding — with waiver records, remittance and reconciliation. A settlement cannot be paid while any line's contribution is unresolved, and the blocking lines are named. The contribution is pApAmA's and is never deducted from the Food Partner's payout. Built
F-2 Nobody pays themselves. The preparer cannot approve their own settlement; a locked settlement can only be amended by reopening it into a new version that needs fresh approval; a material change after approval voids that approval; a rejection needs a reason; whoever placed a hold cannot release it; and a Food Partner bank-account change needs four eyes, with the person who changed it barred from approving payment to the new account. The checker sees the evidence — meal value, difference, contribution status and, where waived, who authorised it and why — beside a three-way reconciliation of pApAmA's records against the claim against the contribution position. Built
F-3 Audit that cannot be quietly undone. Each cycle records its selection — population, sample, who, when — with at least one settlement always selected and no way to remove a row once chosen. Risky transactions raise themselves into an exception queue: reissues, bank changes, unusual waivers, duplicate offline captures. Clearing one requires a note. Built
F-4 Unspent value returns to the Meal Pool. A ₹60 token spent on a ₹50 meal moves ₹10 to the pool, not to revenue; expired value goes the same way instead of being written off. The counter screen now says “returned to Meal Pool” rather than “forfeited”, because that is what happens. Built
F-5 Oldest token first. Allocation serves the oldest eligible pool token, honouring scope and type; a token whose area excludes the volunteer's district is skipped and the skip is counted, so nothing disappears silently. Built

Lane 3 — Emergency framework

6 built
RefWhat it doesStatus
E-1 An emergency is a record, not a switch. Each one carries an ID in the form TN-FLOOD-2026-001, its area, its period, who activated it and its closure reconciliation. Every donation, token and redemption during it is traceable to that ID, and an emergency token cannot be issued without an active record. Built
E-2 Relief without relaxing the books. Inside an active emergency the face step can be skipped with the verification level recorded, and the ₹10 is waived automatically by the system — never at a Food Partner's or volunteer's discretion. The partner is still settled the full meal value, and the waiver ends when the emergency does. Built
E-3 After the emergency, a review queue. Closure populates it with flagged transactions only — rapid repeats, reused identifiers, volume and waiver anomalies — while ordinary transactions stay under the 10% random audit. Built
E-4 Offline capture, emergency only. When the network drops during an emergency, the Food Partner's counter records the meal on the device and it syncs later as Pending Offline Validation — never as a completed redemption. The same token captured on two devices flags both and accepts neither. Expiry, area and status are re-checked on the server, and the device stores a one-way fingerprint of the token, never the redeemable code, so a lost phone yields nothing. It ships switched off: an exception that is on by default is not an exception. Built
E-5 A volunteer facing a problem has somewhere to put it. Eleven one-tap categories — partner closed, no food, token refused, safety concern and the rest — filed in two taps, with the note optional because nobody types while standing in a queue. Safety reports sort to the top of the admin queue regardless of age. Built
E-6 Appeals that cannot be sent by accident. Templates need approval before dispatch; the pre-approved instant template raises a post-send review task; donations that arrive from an appeal carry the Emergency ID. Dispatch is built channel-abstract, so adding SMS or WhatsApp in Phase 2 is a new adapter rather than a redesign. Built

Lane 4 — Privacy

3 built
RefWhat it doesStatus
P-1 Donors learn about the meal, not the person. Notifications carry only the permitted fields — token type and value, date and time, Food Partner at city and state, Emergency ID, programme. A Special Care redemption tells the donor “SPECIAL CARE” and “City, State”; the beneficiary's category is structurally unable to reach the message, which is asserted on the payload itself rather than on the template wording. Built
P-2 Need-to-know screens. The counter sees token type, value and validity; volunteer screens carry the transaction minimum; category data stays with the admin roles whose work requires it. Built
P-3 Every export is logged. Who exported which report, when, and with which filters. Built

Section three

What remains

Two lists, because they move at different speeds. Ours is work; the client's is answers.

With us

5
  1. The last five acceptance checksTwenty of twenty-five are done. The five that remain are held up only by missing test data and a second administrator login, both of which we can arrange with the client’s help.
  2. The maker-checker demonstrationTen happy-path steps and five exception scenarios, shown live. The client’s sign-off on the financial controls depends on seeing it; it needs two administrator logins, and a date is ours to propose.
  3. Post-emergency review split by sourceOffline captures are reviewed after an emergency; the review does not yet separate Food Partner captures from volunteer ones, which the design requires.
  4. Volunteer offline captureThe Food Partner route is built and is the primary one. The volunteer route shares the same server controls but volunteers do not currently hold the permission to use it. We have not granted it quietly — it is a permissions decision to take deliberately.
  5. Donation reconciliation screenOutside the 23, and the one we would start first. Today a donor's own payment reference is accepted with no review, and in pApAmA an unverified donation does not merely inflate a total — it mints tokens that get eaten, leaving a Food Partner owed real money. No donation should become spendable credit without an administrator approving it.

With the client

6
  1. Q-5 — city lock at registrationSoft warning, or drop it? Our recommendation is warn-and-confirm.
  2. Concurrent tokens per volunteerUnset, so the cap correctly tests as not enforced. We will not invent a number for how many tokens one volunteer may hold.
  3. Four offline limitsMaximum pending records per device and per volunteer, the sync window, and the alert threshold. Unset for the same reason.
  4. Rejected offline captures at settlementCurrently set to “review”, which deliberately decides nothing. The real choice — pay, withhold, or review case by case — is the client's.
  5. One Food Partner has no address“Dhruv” cannot be area-checked until an address is on record — it only needs adding to the partner’s details.
  6. The payment routeSB Collect, SBIePay or a commercial gateway. Assessed separately; SBIePay charges nothing on UPI, which is where most donations will come from. A written quote settles it.

Section four

Stated plainly

Four things are deliberately not finished, and should not surprise anyone later

Payment is still simulated apart from manual UPI reference entry — no real money moves until the gateway decision above is made. No email is sent; the official account is an external dependency. Offline capture ships switched off, by design, and stays off until the client sets its four limits. SMS and WhatsApp appeals are Phase 2, pending DLT and WhatsApp Business registration — the Phase 1 architecture is built so they slot in without rework.

What the 18 August decisions changed, and where

All of them are reflected in the register above: validity dated from issue for donor-controlled tokens and from distribution for pApAmA-distributed ones; both offline capture routes with a mandatory source on every record; revalidation retired in favour of controlled reissue; the existing settlement status names kept with a documented mapping, and approval and payment recorded as separate events; the appeal workflow split with the channel-extensibility requirement honoured.
